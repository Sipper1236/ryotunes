## Ryotunes: separate metadata from playback

Ryotunes documents metadata-only mode as opening Spotify in the system browser, finding the `sp_dc` cookie in supported browser stores, exchanging it for a short-lived web token, and calling Spotify Pathfinder. It does not establish a librespot session in this mode; playback is resolved through YouTube Music. The documented catalog includes search, item details, and saved-library lists, while playlist edits, home feed, and lyrics are listed as unsupported/not implemented. The documentation calls the endpoints internal and subject to change. ([`docs/FREE-SPOTIFY.md`](https://github.com/Sipper1236/ryotunes/blob/0d511a489b823075f426ab88153cf08407f37922/docs/FREE-SPOTIFY.md#L1-L7), [supported operations and limits](https://github.com/Sipper1236/ryotunes/blob/0d511a489b823075f426ab88153cf08407f37922/docs/FREE-SPOTIFY.md#L40-L62))

The provider implements separate branches: metadata mode restores a `WebApiClient` and its sign-in uses the web API tokens; normal mode restores/signs in through librespot. Its comments describe the former as catalog-only and say it skips the Premium check. ([`provider.rs`](https://github.com/Sipper1236/ryotunes/blob/0d511a489b823075f426ab88153cf08407f37922/crates/spotify/src/provider.rs#L61-L120)) The PKCE authorization path omits the `streaming` scope for metadata mode; the web-session constructor is also gated to metadata-only mode. ([`auth.rs`](https://github.com/Sipper1236/ryotunes/blob/0d511a489b823075f426ab88153cf08407f37922/crates/spotify/src/auth.rs#L35-L62), [web-session authorization](https://github.com/Sipper1236/ryotunes/blob/0d511a489b823075f426ab88153cf08407f37922/crates/spotify/src/auth.rs#L168-L212), [`web_api.rs` cookie exchange and Pathfinder](https://github.com/Sipper1236/ryotunes/blob/0d511a489b823075f426ab88153cf08407f37922/crates/spotify/src/web_api.rs#L71-L89), [Pathfinder request](https://github.com/Sipper1236/ryotunes/blob/0d511a489b823075f426ab88153cf08407f37922/crates/spotify/src/web_api.rs#L226-L247))

Documented constraints include Firefox-family and supported Linux Chromium cookie stores, with Chromium `v11` keyring-encrypted cookies unavailable to the current reader. Ryotunes stores a web-session cookie and refresh credential in its Spotify data directory with owner-only permissions; the document correctly treats that cookie as session access. ([`docs/FREE-SPOTIFY.md`](https://github.com/Sipper1236/ryotunes/blob/0d511a489b823075f426ab88153cf08407f37922/docs/FREE-SPOTIFY.md#L54-L62))

## Quackify: browser-derived session plus custom native player

Quackify's README describes a native Android client “without needing a WebView,” but the source shows a WebView-based Spotify login/player session. Its login host starts at Spotify's account login page and constructs an Android `WebView`. The README's claim should therefore be read as not relying on a WebView as the audio player, rather than having no WebView at all. ([README](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/README.md#L1-L13), [`LoginWebViewHost.kt`](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/krespot-core/src/main/java/com/quackify/backend/core/webview/LoginWebViewHost.kt#L55-L70))

The auth code treats possession of `sp_dc` as the logged-in signal and extracts it from Spotify-domain cookies. `WebToken` sends that cookie to `open.spotify.com/api/token`, builds a versioned TOTP query, and stores the returned bearer token. This is an observed private Web Player token flow, not a documented Spotify developer OAuth flow. ([`EncoreAuth.kt`](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/krespot-core/src/main/java/com/quackify/backend/core/auth/EncoreAuth.kt#L350-L380), [`WebToken.kt`](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/krespot-core/src/main/java/com/quackify/backend/core/auth/WebToken.kt#L33-L77)) Its Pathfinder client uses Spotify's private `/pathfinder/v1/query` and `/v2/query` endpoints, with seeded operation hashes and code that scrapes Web Player bundles to refresh hashes. ([`Pathfinder.kt`](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/krespot-core/src/main/java/com/quackify/backend/core/net/Pathfinder.kt#L33-L56), [`BundleHashes.kt`](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/krespot-core/src/main/java/com/quackify/backend/core/net/BundleHashes.kt#L34-L48), [scrape flow](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/krespot-core/src/main/java/com/quackify/backend/core/net/BundleHashes.kt#L86-L115))

For audio, Quackify has its own player, DRM-license callback, and manifest logic. `AudioSource.resolvePlayplay` logs that when direct file IDs are absent “free accounts only get drm manifests,” then returns to the fallback path; `AudioEngine` submits the device CDM challenge to the license URL. This is strong source evidence of an intended free-account DRM route. It does not, by itself, establish that every account/region/device succeeds in practice: Quackify labels itself beta, and its README does not document a free-account compatibility guarantee or live-test results. ([`AudioSource.kt`](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/krespot-player/src/main/java/com/quackify/backend/player/AudioSource.kt#L254-L265), [`AudioEngine.kt`](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/krespot-player/src/main/java/com/quackify/backend/player/AudioEngine.kt#L58-L81), [beta notice](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/README.md#L12-L22))

**Reuse/licensing caveat:** the root README presents Quackify as GPL-3.0, while `krespot-player/.../AudioSource.kt` has a file-level notice calling the module proprietary/source-available and prohibiting copying, modifying, distributing, or integrating it without written permission. These statements conflict. This report makes no legal determination; do not recommend porting that player code unless the owner clarifies the applicable license in writing. ([root `LICENSE`](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/LICENSE), [`AudioSource.kt` notice](https://github.com/23fpsz/Quackify/blob/b7444e198a8506adab9d05cf44ad6a2a839bb455/krespot-player/src/main/java/com/quackify/backend/player/AudioSource.kt#L11-L18))

## MySpoti / Orpheon: Web Player services and a native playback engine

The upstream README says users sign in on Spotify's own page and a free account is enough, while also warning that some new or free accounts are refused by Spotify. Its architecture description assigns catalog/search/library reads to direct HTTP requests and uses a hidden Web Player WebView plus bridge for playback and other page services. ([sign-in and free-account note](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/README.md#L36-L40), [account refusal limitation](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/README.md#L134-L151), [architecture](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/README.md#L161-L172))

The API module README specifies the seam: reads use HTTP with the page's web token and an app-minted client token; playback, library writes, folders, Connect, and Jam use the page's services/bridge. It says its listed API coverage is exercised by live `host-cdp` tests against a free account, and separately lists free-account Web Player limits. These are project-authored test claims, stronger evidence than an implementation-only inference, but not a guarantee for all users. ([`base/api-spotify/README.md`](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/base/api-spotify/README.md#L13-L34), [limits](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/base/api-spotify/README.md#L41-L48)) The implementation asks the page bridge for `token.get`, caches the page token, and sends direct Spotify requests with Bearer, client-token, WebPlayer platform, and app-version headers. ([`Gql.kt`](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/base/api-spotify/src/main/kotlin/app/myspoti/spotify/gql/Gql.kt#L186-L228))

At this snapshot, the project also has a native audio engine. `NativeAudio` implements account audio and a listen-sync mirror, uses Media3 and device Widevine, and leaves the Web Player as the account's state/queue/token remote. Its setting defaults to enabled in the code. When native playback fails, the code leaves it aside for 15 minutes and lets the page play. ([`NativeAudio.kt`](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/base/app/src/main/java/com/music/spotui/di/NativeAudio.kt#L36-L74)) The repository's native-playback protocol notes state that their measured free-account sequence used apresolve, Dealer/Connect state, storage resolution, Widevine licensing, CDN audio and playback telemetry; they report three plays confirmed in Spotify history. Those notes identify captures and explicitly distinguish measured facts from inferred details. ([`NATIVE-PLAYBACK.md`](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/docs/api/NATIVE-PLAYBACK.md#L1-L22), [sequence and play-count evidence](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/docs/api/NATIVE-PLAYBACK.md#L24-L53))

There is a doc/code drift to keep in mind: the API README says playback “go[es] through the page's own services,” and the main README describes the Web Player page as the player, while the native engine source says the native engine plays the account's songs when enabled (and the preference defaults to enabled). Treat the versioned native engine source and native-playback notes as evidence of the current implementation in this snapshot, and the README architecture as describing the API/page integration layer rather than the whole playback path. ([API README](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/base/api-spotify/README.md#L13-L20), [native engine](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/base/app/src/main/java/com/music/spotui/di/NativeAudio.kt#L36-L60))

The project itself warns that some new/free accounts receive a refusal response. The README also says ads are played as Spotify sends them in the Web Player path, but native-engine comments say an ad given to the account's player is skipped by that engine. This distinction is another reason not to treat one README statement as a complete guarantee about every playback mode. ([README account and ad notes](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/README.md#L134-L151), [engine behavior](https://github.com/kota-zo/myspoti/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/base/app/src/main/java/com/music/spotui/di/NativeAudio.kt#L36-L47))

## Comparison and implications for Ryotunes

**Verified from source:** all three projects use Spotify Web Player-derived credentials and private Spotify web endpoints for at least part of their metadata integration. Ryotunes is deliberately narrower: its free-account mode stops at metadata and delegates audio matching to YouTube Music. Quackify and the current MySpoti/Orpheon source both implement native Spotify playback paths that include DRM handling; MySpoti additionally documents its free-account captures and play-count validation.

**Inference:** Ryotunes' design has substantially less playback complexity and avoids needing to emulate Spotify's device registration, dealer/control channel, audio manifest handling, DRM license exchange, telemetry, and ad behavior. Its trade-off is that playback is an approximate external match rather than Spotify's own stream. If the requested goal is just reliable free-account catalog/library support, the existing split is the smaller architectural target. If native Spotify audio for free accounts becomes a requirement, MySpoti's documented interface boundary and capture/test discipline are useful design references, but the work would be a distinct playback-engine project with a much larger maintenance surface. Quackify can illustrate implementation techniques at source level, but its player module's conflicting license notice makes code reuse inappropriate absent clarification.

**Account and service risk:** all these integrations depend on private, changeable Spotify web behavior rather than a supported Spotify developer API. Their own code/docs show compatibility failures are possible: Ryotunes lists cookie-store limitations; Quackify is marked beta; MySpoti notes Spotify refusals for some new/free accounts. No claim is made here about Spotify's enforcement policy or whether any one integration violates a particular term; this comparison only records the projects' implementation and first-party statements.

## Current upstream note (2026-11-13)

The current Orpheon README describes the official Spotify Web Player, hidden inside the Android app, as the audio player using the device's DRM. It also states that Orpheon does not circumvent DRM or download Spotify audio, and that some free accounts are refused by Spotify. This is a better description of the supported playback path than treating the experimental native engine as the default. Its native engine remains a separate source implementation, while the README's advertised path is the official Web Player. ([current README](https://github.com/kota-zo/Orpheon/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/README.md#L36-L40), [DRM and refusal notes](https://github.com/kota-zo/Orpheon/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/README.md#L134-L151), [native engine source](https://github.com/kota-zo/Orpheon/blob/70f323c5e5c3c21305b3177eb681e84ba02ce872/base/app/src/main/java/com/music/spotui/di/NativeAudio.kt))

For Ryotunes, the viable cross-platform option/fallback design is:

1. Keep the current browser-cookie + Pathfinder route for free-account metadata (it already covers the Quackify-style metadata approach).
2. Offer official Spotify Web Player playback only when a supported local browser engine with Widevine is available; preserve Spotify's own ads and account restrictions.
3. Keep YouTube Music as the working audio fallback, with an automatic mode that falls back when the Spotify player cannot start or loses DRM support.
4. Do not port Quackify player code while its file-level proprietary notices conflict with its GPL repository license. Treat Orpheon's native playback engine as an experimental, separately selected backend; its protocol and DRM requirements are not supplied by the Android source alone on Linux.

On the inspected Ryotunes host, Chromium and Firefox are installed but no Widevine CDM was found under `/usr/lib` or `/opt`; the Ryotunes daemon uses WebKitGTK 2.54.2. WebKitGTK has EME support, but that does not provide a Widevine CDM. This is host-specific evidence and should be checked at runtime rather than assumed. ([WebKitGTK multimedia documentation](https://docs.webkit.org/Ports/WebKitGTK%20and%20WPE%20WebKit/Multimedia.html), [Widevine platform support](https://developers.google.com/widevine/drm/overview))

## Ryotunes implementation decision

Ryotunes keeps Spotify free-account support metadata-only: Pathfinder supplies Spotify search and
library data, while every Spotify song plays through the existing YouTube Music duration-checked
fallback. The user rejected an external Spotify playback backend because launching a separate
Spotify Web Player browser tab is surprising and does not provide integrated Ryotunes playback.
The Chromium/CDP adapter explored during this comparison has therefore been removed from the
branch. Quackify player code was not reused due to its conflicting license notices; Orpheon's
Android WebView/DRM stack is not a drop-in Linux playback engine.

The existing fallback checks the selected queue row's Spotify ID, title, artist and duration,
searches YouTube Music, chooses a close-duration candidate when available, and resolves that
YouTube ID through the normal stream orchestrator. This host-specific branch run did not establish
why a particular user's liked track failed after the external player attempt; the UI and daemon
must be exercised together to confirm the fallback against that account and current YouTube
availability.
